Write a Python 3 file, verify.py, the verification runner for ParcelCheck. Standard library only. It imports checker (same folder) and scores the frozen checker against a sealed answer key.

Setup: prep folder is PARCELCHECK_DIR env var else the script's folder; insert prep into sys.path; import checker. The ten scored listing ids, in order: L02, L03, L04, L05, L06, L08, L09, L10, L11, L12. Point numbers map 1..9 to: access, flood, perc_septic, water_well, liens_tax, zoning, utilities, mineral_timber, survey. Key status words map: "problem stated" -> problem_stated, "clean" -> clean, "missing" -> missing.

Step 1, seal check: sha256 of answer-key.md in prep must equal the first token of answer-key.sha256; assert with a clear mismatch message; print "seal verified:" plus the first 16 hex chars.

Step 1b, key preflight: if meta-api-key.txt does not exist in prep, print "STOP: meta-api-key.txt not found next to verify.py. No runs attempted, no files written." and exit with code 2. (Without the key every run would fail and this script would overwrite the published results with zeros.)

Step 2, parse the key: for each listing id, find its section in answer-key.md (starts "## LID:" and runs to the next "## " heading, a line starting "No problem", or end of file). In the section, table rows look like "| 3 | Perc / septic | problem stated | ... |": capture the number and the status words; build {point: status}; assert exactly 9 rows per listing.

Step 3, run and score: keep an executed counter (listings that produced a result object, including invalid-output ones) and totals: points, correct, prob_key, prob_caught, false_flags, miss_key, miss_named, clean_key, clean_ok, usd. For each listing: read listings/LID.txt, take the text after the first blank line, stripped. Call checker.check(text, lid).
- On exception: add a results section "## LID: RUN FAILED (<error, first 120 chars>). Tokens logged in runs.jsonl. Scored as no points matched."; detail entry {"error": first 200 chars}; add 9 to points and add the key's problem/missing/clean counts to prob_key/miss_key/clean_key; continue (executed NOT incremented).
- If the result has harness errors or no "checks" key: section "## LID: INVALID OUTPUT (<errors joined, first 200 chars>). Scored as no points matched."; executed += 1; detail {"invalid": errors, "cost": result cost}; add cost; add 9 points and key category counts as above; continue.
- Otherwise: executed += 1; got = {point: status}; detail {"got": got, "cost":..., "harness":...}; add cost. For each point: points += 1; category counters per key status; prob_caught when key problem_stated and got problem_stated; miss_named when key missing and got missing; clean_ok when key clean and got clean; false_flags += 1 when got problem_stated and key not problem_stated; correct when equal, else collect a miss line "point: key X, got Y". Section header "## LID: N/9 points match, cost $X.XXXX" followed by "- MISS: ..." lines, and a "- HARNESS ERRORS: ..." line if any.

Step 4, output: the results markdown starts "# ParcelCheck verification results", blank, "Answer key sha256 verified before the run: <digest>", blank, "Prompt: v1 (frozen). Model: muse-ember-1.0. One structured pass per listing.", blank; insert at line index 4 a bold totals line: "**Totals across <points> points: <correct> exact matches. Problems in key: <prob_key>, caught: <prob_caught>. False problem flags: <false_flags>. Missing in key: <miss_key>, named missing: <miss_named>. Clean in key: <clean_key>, called clean: <clean_ok>. Total cost of the ten runs: $<usd 4dp>.**" If executed == 0: print "STOP: no listing produced a result (every run failed). Published results left untouched." and exit 1 WITHOUT writing. Else write verification-results.md and verification-detail.json (the detail dict, indented) into prep, print the first 8 lines and "written verification-results.md".

Module docstring: verifies the sealed key hash, runs the frozen checker over the ten untouched listings, scores after the runs (the checker never sees the key), writes verification-results.md.

Correction pinned after a failed validation run (read carefully): the checker result object carries a "harness" DICT of the form {"errors": [...], "warnings": [...], "seconds": ..., "prompt_version": ..., "rules_applied": [...]}. A result is INVALID only when harness["errors"] is a non-empty list OR the result has no "checks" key. Never test the harness dict itself for truthiness: it is always non-empty, and doing so marks every successful run invalid. In the INVALID branch, the message shows the harness errors list joined with "; ", the detail entry is {"invalid": <the errors list>, "cost": result["cost"]}, and the run's cost IS added to the totals.

Second correction pinned after another failed run: the checker result's "cost" is a DICT {"usd": float, "input_tokens": int, "output_tokens": int, "model": str}. Totals must add cost["usd"] (a float, 0.0 when cost is absent), never the dict itself. Detail entries store the full cost dict as returned. A helper that extracts cost must return the float for totals and the dict for detail, or handle the two uses separately; do not add a dict to a number anywhere.
